# Tenant Billing Demo

This demo workspace models a small multi-tenant SaaS back office. It is intentionally compact in code, but it still shows a realistic set of responsibilities that agents and developers ask about when they are dropped into an unfamiliar repository: authentication, tenant scoping, billing, notifications, jobs, reports, and support operations. The JavaScript/TypeScript code path is designed so that a graph can surface the important entities quickly. The surrounding prose remains ordinary repository material that an agent can read directly when a task needs it; Madar does not add those documents to the graph.

The runtime entrypoint lives in `src/app.ts`. It wires a tenant-aware auth service, a billing flow that can issue invoices and receipts, a monthly close job, and a report generator used by finance. The important business concepts are split into focused modules. `src/auth/` handles password policy checks and session creation. `src/shared/tenant-context.ts` defines the tenant identity passed through the rest of the system. `src/billing/invoice-service.ts` coordinates invoice work and passes email delivery to `src/notifications/email-notifier.ts`. `src/jobs/monthly-close-job.ts` triggers the monthly billing close and asks `src/reports/revenue-report.ts` to build the summary that finance reviews at the end of the month.

The code intentionally reflects the kinds of questions a developer would ask in a code review, onboarding session, or incident response. They want to know how password login becomes a tenant session, which module is responsible for invoice receipts, what runs the monthly close, how the revenue report is built, and where tenant context is defined. Those questions are frozen in both benchmark files. `benchmark-questions.json` preserves the historical mixed container/file-label gold so older scores remain comparable. `benchmark-questions.v3.json` is the active Core Reset contract: it grades authenticated declaration evidence and direct call-path owners, not structural file labels that ordinary non-structural queries intentionally omit.

This workspace also includes narrative documentation because real projects almost always do. Teams keep architecture notes, operational runbooks, design rationale, and process guidance alongside code. Those files are intentionally outside Madar's canonical JavaScript/TypeScript index and appear as unsupported coverage rather than graph evidence. This makes the boundary visible: start with the focused code graph, then read a specific document directly only when the question actually depends on it.

Nothing in this workspace depends on a database or an external service. The implementation itself stays local and deterministic so the demo corpus is easy to generate in CI and in a fresh checkout. Comparative proof uses the development-only frozen evaluators under `tools/eval/core-reset`; those runners are repository tooling, not public CLI commands. This tiny corpus is a correctness and regression fixture, not evidence that Madar reduces tokens: the serialized evidence can be larger than all 12 source files combined. Token and time claims require the frozen real-repository and provider-backed comparisons; this demo only proves whether the declared code paths remain retrievable.

If you want to adapt this demo for your own presentations, keep the same shape. Use a JavaScript/TypeScript repository with a few well-named modules, a small labeled question set, and enough unrelated repository material to make broad exploration meaningfully larger than the critical code paths. Keep claims tied to indexed code facts and treat unsupported files as an explicit verification boundary.
